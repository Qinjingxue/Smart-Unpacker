# sunpack repair_training 训练体系分析

## 一、体系定位

`repair_training` 是一个**离线强化学习管道**，目标是为 sunpack 的存档修复模块训练一个 **Q 值预测模型**，用来在修复过程中从多个候选方案（candidate）中选择预期回报最高的那个。

核心思路：

```
损坏的存档 → 生成多个修复候选 → 用 Q 模型给每个候选打分 → 选最高分执行 → 进入下一轮修复
```

训练数据并非来自在线交互，而是通过**结构化损坏 + 多轮回放**的方式离线构造状态-动作-奖励转移。

---

## 二、五阶段管道

### 阶段 0：源材料 (`source_material/`)

`source_material/<sample_id>/` 下是普通文件夹，包含任意文件（`.txt`, `.bin` 等）。这些就是"干净数据"——后续一切存档的原始内容。

当前有 30 个样本文件夹（`122`, `22`, `222`, `333`, `IM`, `nginx`, `TSF` 等）。

### 阶段 1：存档派生 (`derive_archives.py`)

将源文件夹打包成**干净的存档文件**，输出到 `material/<format>/<sample_id>/`。

- **支持格式**：zip, 7z, rar, tar, gzip, bzip2, xz, zstd, tar.gz, tar.bz2, tar.xz, tar.zst
- **工具链**：Python 原生 (zipfile/tarfile/gzip/bz2/lzma) + 外部工具 (7z.exe, rar.exe, zstd.exe)
- **ZIP 有 12 种变体**：

| 变体 | 说明 |
|------|------|
| `normal_deflate` | 标准 Deflate 压缩 |
| `normal_store` | 仅存储不压缩 |
| `mixed_store_deflate` | 混合压缩方法（交替 store/deflate） |
| `data_descriptor_bit3` | 使用数据描述符替代本地头部 CRC |
| `long_comment` | 超长 EOCD 注释（2048 字节） |
| `sfx_stub` | 假冒 SFX 前缀（模拟自解压载体） |
| `duplicate_entries` | 重复条目名 |
| `zip64_forced` | 强制 zip64 扩展字段 |
| `non_utf8_names` | 非 UTF-8 文件名（CP437） |
| `split_zip` | 分卷 ZIP |
| `sfx_split_zip` | SFX + 分卷 ZIP |
| `encrypted_zipcrypto` | ZipCrypto 传统加密 |

- **采样策略**：`random_mode` 默认开启，使用 `balanced_format` 策略按权重随机选取，避免组合爆炸。配置在 `archive_derivation_config.json`。
- **输出**：`material/<format>/<sample_id>/<name>.zip` 等 + `.derived.json` 元数据侧车文件。

### 阶段 2：损坏案例生成 (`build_repair_plan_corpus.py`)

对每个干净存档施加**结构化二进制损坏**，输出到 `material/<format>/<sample_id>/damaged/`。

核心实现：`training_corruption.py` 中的 `BinaryCorruptor` 类 + `CorruptionCase` 数据结构。

**损坏操作类型**（基于 `PatchOperation`）：
- `replace_byte` / `replace_bytes` — 翻转/替换特定偏移的字节
- `truncate` — 从指定位置截断
- `append` — 在末尾追加噪声
- `insert` — 在中间插入噪声
- `delete` — 删除一段字节
- `combine_mutations` — 组合多种操作

**六层损坏分布**（`PROFILE_LAYERS`，带权重）：

| 损坏层 | 权重 | ZIP 预算 | 说明 |
|--------|------|---------|------|
| `structural` | 0.30 | 1 | 边界/头部/尾部损坏 |
| `structural_directory` | 0.30 | 3 | CD/EOCD/目录结构损坏 |
| `partial_recoverable` | 0.25 | 1 | 单条目负载损坏、截断 |
| `hard_negative` | 0.15 | 2 | 全部条目损坏（不可修复） |
| `two_step_repair` | 0.20 | 5 | 复合损坏需要多轮修复 |
| `deceptive_hard_negative` | 0.30 | 3 | 看似可修但产出坏数据 |

ZIP 特有设计：`_zip_structure_target_profile()` 根据源存档的实际 ZIP 变体（SFX / 分卷 / data_descriptor 等）**定向选择匹配的损坏模式**，保证损坏模式的真实性和针对性。

每个 `CorruptionCase` 包含：
- 损坏前后的二进制数据 + SHA256
- 损坏操作的精确描述（offset, size, zone）
- 预期修复结果（oracle）：expected_statuses, expected_module, expected_files
- 难度标签（difficulty_tags）、oracle 强度（oracle_strength）
- `regression_snippet()` 生成可复现的测试代码

**输出**：`material/<format>/<sample_id>/damaged/<source>/vNNN/<name>.damage.json` + `damage_manifest.jsonl`

### 阶段 3：回放数据采集 (`collect_repair_plan_data.py`)

这是整个管道最复杂的部分。对每个损坏案例，运行 sunpack 的真实修复管道，**采集状态-动作-奖励转移**。

**核心流程**（`_collect_sample_rows`）：

1. 创建 `RepairJob`，注入损坏输入 + 分析证据 + 模糊特征（entropy, byte class, ngram）
2. `RepairScheduler.generate_repair_candidates()` 生成候选修复方案
3. 用 `CandidateSelector` 排序/选择候选
4. 对候选进行物化（materialize）+ 原生验证（native validation via 7z.dll wrapper）
5. 对每个候选，模拟执行后的验证结果来打标签
6. 采集为 RL 转移行：state → action → reward → next_state

**四种回放模式**（`--rollout-mode`）：

| 模式 | 行为 |
|------|------|
| `greedy` | 每轮取 generation_priority 最高的候选 |
| `greedy_current_selector` | 使用真实的 CandidateSelector（eager 模式，实际执行修复） |
| `beam` | 每轮保留 top-K 分支并行推进 |
| `counterfactual` | 额外探索 risky/high-value 的替代路径（反事实推理） |

**标签体系**（label）：
- `-1` = hard_negative（验证失败，产出错误数据）
- `0` = no_output / 未物化 / 候选不可用
- `1` = partial（部分恢复）
- `2` = repaired（完全修复）
- `3` = terminal_success（终端成功，所有轮次累积）

**RL 信号计算**：
- `reward`：基于终端恢复率的即时奖励
- `discount`：0.95
- `future_return`：从当前动作到终端的折扣累积奖励（Q 值目标）
- `step_cost`：每步 -0.01
- `no_output_penalty`：-0.05（死胡同惩罚）
- `hard_negative_penalty`：-0.10（产生错误输出的惩罚）

**特征提取**（`runtime_features.py`，`FEATURE_CONTRACT_VERSION = 2`）：

- **analysis_summary**：格式检测结果、置信度、预检测状态
- **analysis_native_probe**：原生分析数据（ZIP 结构特征、预检测命中计数、模糊二进制画像中的 entropy / byte_class / ngram / source_derivation 字段）
- **fuzzy_profile**：熵分布（head/middle/tail）、字节分类（printable/control/high_bit/zero/ff）、ngram 草图、游程编码特征
- **extraction_summary**：提取诊断、失败阶段/类型、进度事件计数、worker 进程状态
- **verification_summary**：完整性评估、文件覆盖、archive_coverage 详情
- **verification_per_file**：逐文件状态（CRC 匹配/不匹配计数、截断计数、各状态文件数）
- **repair_hints**：修复提示（边界不可信、负载损坏标记、segment 起止、damage_flags）
- **candidate_proposal**：候选方案特征 + LTR 特征 + ZIP 计划风险特征（目录置信度、偏移置信度、no_output 风险评分）
- **repair_prior_features**：路由评分、选择器排名、proposal_breakdowns
- **native_feedback**：从候选诊断中提取的原生修复反馈

**采集控制**：
- 超时管理（`case_timeout_seconds`，默认 45s，超时则杀进程）
- 状态预算上限（`max_total_states_per_sample`，默认 6）
- 大流式样本特殊处理（gzip/bzip2/xz/zstd 超过 `stream_large_size_mb` 阈值可跳过或降预算）
- 支持多进程并行（`mp.Process` + pickle 通信）
- 全局超时（`total_timeout_seconds`）和空闲超时（`idle_timeout_seconds`）
- 心跳日志（`heartbeat_seconds`，默认 5s）

**输出**：`datasets/repair_plan_ltr_{success,failure}_<strategy>.jsonl`

### 阶段 4：离线 RL 训练 (`train_offline_rl.py` / `train_slim_rl.py`)

用采集到的转移数据训练 **LightGBM 回归模型**来预测 `future_return`（Q 值）。

**训练架构**：
- **模型**：`LGBMRegressor`（梯度提升树，LightGBM）
- **目标**：`future_return`（或 `reward` / `terminal_reward`）
- **特征向量化**：`DictVectorizer`（稀疏矩阵，one-hot + 数值混合）
- **分裂策略**：按 `source_sample` 80/20 分层（避免同源数据泄漏到评估集）
- **默认超参数**：n_estimators=300, learning_rate=0.04, num_leaves=31, min_child_samples=20

**两种特征视图**：
- `runtime_only`：~219 维 —— 纯运行时上下文特征（不含 oracle 特征）
- `runtime_plus_repair_prior`：额外加入修复先验特征（route_score, fine_score 等）

**Slim 变体** (`train_slim_rl.py`)：
- 只用 4 组状态特征 + `candidate.module`，约 45-55 维
- 保留前缀：`verification_summary`, `verification_per_file`, `extraction_summary`, `job_summary`, `repair_hints`, `fuzzy_profile`, `analysis_native_probe`, `native_feedback`
- 目标：验证精简特征集能否接近完整模型性能
- 默认超参数：n_estimators=500, learning_rate=0.03, num_leaves=63（更深的树补偿特征减少）

**评估指标**：
- R²、MAE、RMSE（回归质量，在 eval 集上）
- **策略悔恨**（Policy Regret）：在 eval 集上模拟 top-1 选择 vs oracle 选择，计算 expected return 差距
- top1_future_return_mean / oracle_future_return_mean / regret_p90

**输出**：`models/offline_rl/<name>/` 下的：
- `model.txt` — LightGBM booster 模型文件
- `vectorizer.joblib` — sklearn DictVectorizer
- `feature_names.json` — 特征名列表
- `metrics.json` — 评估指标
- `predictions.jsonl` — 逐样本预测详情
- `training_summary.json` — 训练摘要

当前已有 5 个模型变体：
- `zip_q_value` — 标准模型
- `zip_q_value_b_budget` / `zip_q_value_b_budget_fixed_names` — 预算约束变体
- `zip_q_value_slim` / `zip_q_value_slim_v2` — 精简特征变体

### 阶段 5：离线策略评估 (`evaluate_offline_policy.py`)

在观测到的回放图（rollout graph）上**回放不同策略**，评估实际表现。

**策略对比**：
- `current_selector`：当前系统选择器（generation_priority 最高者）
- `random`：随机选择（用于基线）
- `oracle_upper_bound`：取真实 future_return 最高的候选（理论上界）
- `ltr:<name>`：加载训练好的 LTR 预测分数来选（学习到的策略）

**评估流程**：
1. 从 JSONL 行构建状态-动作图（`_build_graph`）
2. 对每个 episode 的根状态，按策略逐步选择动作推进
3. 最多 `max_steps`（默认 20）步
4. 记录终端恢复率、episode 回报、步数等

**指标**：
- `mean_terminal_recovery`：平均终端恢复率
- `mean_episode_return`：平均 episode 累积回报
- `mean_regret_vs_oracle`：与 oracle 的平均差距（越低越好）
- `no_output_rate`：死胡同动作比例
- `hard_negative_rate`：产生坏输出的动作比例
- 按 `damage_profile` 和 `first_module` 分组统计悔恨（识别薄弱场景）

**输出**：`datasets/offline_policy_evaluation_<strategy>.json`

## 五、关键设计决策

1. **离线优先**：不使用在线 RL（不需要环境交互），所有转移从回放图中构建。"环境"就是 sunpack 的修复管道本身，但采集是一次性的，之后可以反复训练。

2. **Oracle 驱动标签**：每个损坏案例都有 ground-truth oracle（预期模块、预期文件、预期状态），标签来自实际修复验证而非启发式规则。这是训练数据质量的基础保障。

3. **特征版本化**：`FEATURE_CONTRACT_VERSION = 2`，允许特征 schema 演进而不会静默破坏旧模型。训练和推理使用同一份 `runtime_features.py` 代码抽取特征。

4. **ZIP 深度特化**：针对 ZIP 的各种变体（SFX、分卷、data descriptor、zip64 等）有定向损坏和特征提取逻辑。`_zip_structure_target_profile()` 和 `_zip_plan_risk_features()` 是 ZIP 专有的高级特征工程。

5. **复合损坏与对抗样本**：`two_step_repair` 需要多轮修复才能恢复，`deceptive_hard_negative` 在第一轮看起来可修但实际产出错误数据。这些困难案例是训练模型鲁棒性的关键。

6. **特征消融验证**：`train_slim_rl.py` 将特征从 ~219 维压缩到 ~45-55 维，主动验证哪些特征组对 Q 值预测真正有贡献。当前对比基线：Full R²=0.9814, MAE=0.0203, Regret=0.00072。

7. **严格的架构边界**：训练代码不导入 sunpack 内部的 `internal` 模块，遵循项目的 `AGENTS.md` 中规定的域边界约束。

8. **Windows 专属**：所有脚本在顶部强制检查 `$env:OS -ne "Windows_NT"`，训练管道目前仅在 Windows 上运行。

9. **多进程超时安全**：采集阶段使用 `multiprocessing.Process` + pickle 文件通信，支持单样本超时杀进程（含递归杀子进程），避免了卡死在某个损坏案例上的问题。

10. **数据集组织**：成功和失败案例分文件存储（`success` vs `failure` JSONL），数据集目录下有大量按策略命名的文件（如 `zip_terminal_recovery`, `zip_four_step_enhanced`, `zip_oracle_b_budget` 等），表明团队在做大量的策略对比实验。
